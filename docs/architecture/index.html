MindOS 架构图

MindOS 是一个本地 Markdown 知识库，加一个把多个外部 AI agent 接进来、让它们共享这个知识库的宿主。 所有客户端都是外壳，业务集中在产品核心 @geminilight/mindos；数据落在你本机。 点击任意模块查看职责、关键文件和它连向谁；悬停可高亮它的连线。

悬停或点击一个模块，显示它的连线 调用 / 依赖方向 产品核心

产品核心 packages/mindos/src 的依赖箭头只能单向： foundation ← knowledge ← agent ← server，protocols 是低层 domain。 这条规则由 packages/mindos/src/layering.test.ts 静态扫描强制执行，例外清单为空——不是约定，是会让 CI 变红的契约。

为什么这样分：同一套业务逻辑被 Web、CLI（packages/mindos/bin）、MCP server 三个入口共用。 分层保证底层（文件、配置、权限）永远不会反向依赖上层（HTTP、agent），所以任何入口都能只取它需要的那一层。

跨层接线：需要"下层调上层"的地方（比如 knowledge 读 agent 的运行数据）一律走 port： 模块加载时由上层安装实现，注册表是 Symbol.for 进程级，Next 多个 bundle 副本共享同一次安装。

两件方向相反的事别混在一起：我们作为宿主去跑 agent（本页上半部分），以及 别人把我们当 MCP server 用（外部 agent 读写这个知识库，是"跨 agent 共享上下文"的实现方式）。

四条 lane：生命周期统一，对话方式不同

所有 lane 的生命周期收敛到一个调用方 agent/runtime/runRuntimeLaneTurn ledger 记录取消 / 超时分类断连宽限capsule

方向是 ACP-first。2026-06 自研 Claude / Codex lane 时，ACP adapter 还不支持 session 恢复。 这个前提在 2026-11 已不成立：codex-acp 底层驱动同一个 Codex App Server，claude-agent-acp 基于同一个 Claude Agent SDK。

所以先把 ACP lane 补齐到 ACP v1 完整能力（一次让 40+ 个 agent 都受益），再让两条专用 lane 退休。 Phase 1 已完成：diff 透传、用量与费用、结构化计划、图片输入、错误不再被吞。

内置 agent：嵌入 Pi 框架

  • Pi 运行时 @earendil-works/pi-coding-agent 1.5.0，进程内运行
  • 扩展：pi-subagents、pi-mcp-adapter、pi-web-access、pi-schedule-prompt（已打补丁，上游停更）
  • MindOS 自有扩展：知识库工具（23 个）、提问桥接、IM、子 agent ledger
  • 与用户自己的 Pi 隔离：状态放在 ~/.mindos/pi，从不读写 ~/.pi；派生子进程时把 PI_CODING_AGENT_DIR 还原成用户原值

权限：一条阶梯

只读计划询问（默认）自动完全
  • 「计划」是权限的一档：服务端对计划强制只读（agent-turn-service.ts）
  • 「目标」不是权限，从输入框的 + 菜单设定
  • 线上契约不变：permissionMode 仍是 read|ask|auto|full，映射收敛在 lib/agent/composer-permission.ts

反方向：被外部 agent 当 MCP server 用

MCP server

  • 源码 packages/mindos/src/protocols/mcp-server，发布为 dist/protocols/mcp-server/index.cjs
  • 传输：stdio（agent 直接 spawn）或 HTTP（/mcp，Bearer Token）
  • 38 个 mindos_* 工具：读写文件、空间、CSV、bootstrap 等

谁在用

  • 27 个 MCP agent 的配置路径由 agent/config/registry.ts 统一维护（Claude Code、Cursor、Windsurf、Gemini CLI、Kimi、Qwen …）
  • MindOS 能一键把自己写进这些 agent 的 MCP 配置，或复制 Skill 过去
